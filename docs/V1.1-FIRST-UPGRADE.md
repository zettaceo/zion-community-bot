# ZION v1.1 — First Production Upgrade Procedure

Status: **prepared only — do not execute until production authorization and external gates are complete**.

This procedure exists because the current v1 production commit predates the v1.1 release-gate scripts. It bootstraps those scripts from the **exact approved candidate SHA** without modifying the existing production worktree.

## Bootstrap trust note

The first upgrade must not trust user-controlled executable lookup for release evidence. The reviewed scripts pin the system executable path and use `/usr/bin/git` for SHA/branch/worktree decisions. Do not substitute the disabled legacy `apply-systemd.sh` or `apply-wifi-guardian.sh` installers if a release gate fails.

## Hard prerequisites

Do not proceed until all are true:

- GitHub `zion-v1` protection/ruleset is enabled and verified;
- PR #2 has received the intended final review and its exact head/merge result is known;
- required ZION CI is green for the exact production candidate;
- Tailscale/OpenSSH host acceptance in `docs/REMOTE-ACCESS.md` is complete;
- router/NAT has no public TCP/22 forwarding;
- Tailnet policy and device identity are verified;
- physical/recovery access to the Acer exists;
- the current ZION production service is healthy;
- no unrelated local changes exist in `zion-v1-prod`;
- repository-local ignored importable artifacts (for example loose `.pyc`/`.so` or stale code `__pycache__`) have been inventoried and are absent outside intentionally isolated runtime/editor directories.

## 1. Record current production before the remote merge

On the Acer:

```bash
cd /home/zetta/zion-community-bot

PATH=/usr/sbin:/usr/bin:/sbin:/bin
export PATH

SAFE_GIT_SSH_COMMAND="/usr/bin/ssh -F /dev/null -o BatchMode=yes -o StrictHostKeyChecking=yes -o ProxyCommand=none -o ProxyJump=none -o PermitLocalCommand=no"

test "$(id -un)" = "zetta"
test "$(/usr/bin/git branch --show-current)" = "zion-v1-prod"
test -z "$(/usr/bin/git status --porcelain --untracked-files=all)"

PREVIOUS_HEAD="$(/usr/bin/git rev-parse HEAD)"
printf 'current production: %s\n' "$PREVIOUS_HEAD"
```

Keep `PREVIOUS_HEAD` in the current shell. Do not put it in Git.

## 2. Merge production PR only after the explicit production decision

This document does **not** authorize merging PR #2.

After the production PR has been explicitly approved and merged in GitHub, record the exact 40-character merge/release SHA as:

```bash
export ZION_DEPLOY_COMMIT=<approved-40-character-sha>
```

Then preflight the **existing** Git authentication/transport configuration before the first network Git command. This bootstrap check is intentionally self-contained because the v1 checkout does not yet contain the v1.1 checker:

```bash
for name in \
  GIT_CONFIG GIT_CONFIG_GLOBAL GIT_CONFIG_SYSTEM GIT_CONFIG_PARAMETERS \
  GIT_CONFIG_COUNT GIT_SSH GIT_SSH_COMMAND GIT_SSH_VARIANT GIT_ASKPASS \
  SSH_ASKPASS SSH_ASKPASS_REQUIRE GIT_PROXY_COMMAND GIT_EXEC_PATH \
  GIT_SSL_NO_VERIFY GIT_SSL_CAINFO GIT_SSL_CAPATH
do
  if [[ -n "${!name:-}" ]]; then
    printf 'ERRO: variável Git/SSH proibida no bootstrap: %s\n' "$name" >&2
    exit 2
  fi
done

BOOTSTRAP_ORIGIN="$(/usr/bin/git config --get remote.origin.url)"
case "$BOOTSTRAP_ORIGIN" in
  "https://github.com/zettaceo/zion-community-bot"|"https://github.com/zettaceo/zion-community-bot.git"|"git@github.com:zettaceo/zion-community-bot.git"|"ssh://git@github.com/zettaceo/zion-community-bot.git")
    ;;
  *)
    echo "ERRO: origin do bootstrap não é o repositório GitHub esperado." >&2
    exit 2
    ;;
esac

/usr/bin/python3 -I - "$PWD" <<'PY'
from __future__ import annotations

import re
import subprocess
import sys

root = sys.argv[1]
safe_helper = re.compile(
    r"^[A-Za-z0-9._-]+(?:[ \t]+[A-Za-z0-9_./:@%+=,~:-]+)*$"
)
pattern = (
    r"^(?:"
    r"core\.askpass|core\.sshcommand|ssh\.variant|"
    r"url\..*\.insteadof|remote\.origin\.uploadpack|"
    r"credential\.(?:.*\.)?helper|"
    r"http(?:\..*)?\.(?:sslverify|sslcainfo|sslcapath)"
    r")$"
)
result = subprocess.run(
    ["/usr/bin/git", "-C", root, "config", "--get-regexp", pattern],
    text=True,
    capture_output=True,
    check=False,
)
if result.returncode not in (0, 1):
    raise SystemExit("ERRO: não foi possível auditar configuração Git do bootstrap.")

for raw in result.stdout.splitlines():
    key, _, value = raw.partition(" ")
    key_l = key.lower()
    value = value.strip()
    if key_l.endswith("helper"):
        if value and safe_helper.fullmatch(value) is None:
            raise SystemExit(
                f"ERRO: credential.helper executável inseguro no bootstrap: {key}"
            )
        continue
    if key_l.endswith("sslverify"):
        if value.lower() in {"true", "yes", "on", "1"}:
            continue
        raise SystemExit("ERRO: Git HTTP TLS verification está desabilitada.")
    raise SystemExit(f"ERRO: override Git inseguro no bootstrap: {key}")
PY

GIT_TERMINAL_PROMPT=0 \
/usr/bin/git \
  -c "core.sshCommand=$SAFE_GIT_SSH_COMMAND" \
  -c ssh.variant=ssh \
  fetch --prune origin zion-v1

test "$(/usr/bin/git rev-parse origin/zion-v1)" = "$ZION_DEPLOY_COMMIT"
/usr/bin/git merge-base --is-ancestor "$PREVIOUS_HEAD" "$ZION_DEPLOY_COMMIT"
```

For SSH origins, the fetch ignores user/system SSH configuration via `-F /dev/null`; host-key verification remains strict and proxy/local-command directives cannot be inherited. For HTTPS origins, the bootstrap rejects executable credential/askpass overrides, URL rewrites, custom CA overrides and disabled TLS verification before the fetch.

Do **not** fast-forward `zion-v1-prod` yet.

## 3. Materialize the candidate release tools without changing production

```bash
PROD_ROOT="/home/zetta/zion-community-bot"
TMP_RELEASE_ROOT="$(mktemp -d /tmp/zion-v11-release.XXXXXX)"
chmod 700 "$TMP_RELEASE_ROOT"

BOOTSTRAP_CHECKER="$TMP_RELEASE_ROOT/check-git-release-boundary.py"
CANDIDATE_ROOT="$TMP_RELEASE_ROOT/candidate"

# Read the checker directly from the approved Git object. This is raw blob
# access: no candidate worktree exists yet and no smudge filter is applied.
env -i \
  PATH=/usr/sbin:/usr/bin:/sbin:/bin \
  GIT_CONFIG_NOSYSTEM=1 \
  GIT_CONFIG_GLOBAL=/dev/null \
  GIT_NO_REPLACE_OBJECTS=1 \
  /usr/bin/git -C "$PROD_ROOT" \
    show "$ZION_DEPLOY_COMMIT:scripts/check-git-release-boundary.py" \
    > "$BOOTSTRAP_CHECKER"

test -s "$BOOTSTRAP_CHECKER"
chmod 600 "$BOOTSTRAP_CHECKER"

/usr/bin/python3 -I "$BOOTSTRAP_CHECKER" --root "$PROD_ROOT"

GIT_NO_REPLACE_OBJECTS=1 \
/usr/bin/git -c core.hooksPath=/dev/null -C "$PROD_ROOT" \
  worktree add --detach "$CANDIDATE_ROOT" "$ZION_DEPLOY_COMMIT"

test "$(GIT_NO_REPLACE_OBJECTS=1 /usr/bin/git -C "$CANDIDATE_ROOT" rev-parse HEAD)" = "$ZION_DEPLOY_COMMIT"
```

The raw checker must pass **before** `worktree add`. This ordering is security-relevant: a local Git attribute/smudge configuration can execute code during checkout even when hooks are disabled. Do not replace the raw `git show <sha>:path` extraction with `checkout`, `archive`, or another worktree-producing command.

The running production worktree remains on `$PREVIOUS_HEAD`.

## 4. Prepare the audited runtime for the exact release SHA

While the old production service remains online:

```bash
ZION_DEPLOY_COMMIT="$ZION_DEPLOY_COMMIT" \
  bash "$CANDIDATE_ROOT/scripts/prepare-release-runtime.sh"
```

This creates or verifies:

```text
/home/zetta/.local/share/zion-community-bot/runtimes/<approved-sha>/
```

and validates it against `requirements.lock`.

For the first migration only, if `runtimes/current` does not yet exist, the preparation script points it at the existing legacy `.venv`. It **does not** switch `runtime/current` to the candidate. The running bot is therefore unaffected.

Any failure stops the release.

## 5. Run strict deployment preflight from the candidate

Refresh sudo credentials only so the read-only SSH effective-config check can use `sudo -n sshd -T -C` when required:

```bash
sudo -v
```

Then:

```bash
ZION_DEPLOY_COMMIT="$ZION_DEPLOY_COMMIT" \
ZION_GITHUB_GATES_PROVEN=YES \
ZION_REMOTE_NETWORK_PROVEN=YES \
  bash "$CANDIDATE_ROOT/scripts/deployment-preflight.sh"
```

This gate verifies its **own worktree HEAD** equals the approved SHA while separately inspecting the old production root.

The local Git boundary also rejects hidden ignore/attribute overrides and ignored importable code. If the old v1 worktree contains stale generated bytecode, stop and inventory it. Remove only artifacts that are proven generated caches; do not bulk-delete an unknown ignored file merely to make the gate green.

Validation itself routes Python bytecode to a private temporary cache under `/tmp`, so the candidate gate does not recreate repository-local `__pycache__`.

Any failure stops the release.

## 6. Run isolated approved-release verification

```bash
ZION_DEPLOY_COMMIT="$ZION_DEPLOY_COMMIT" \
ZION_GITHUB_GATES_PROVEN=YES \
  bash "$CANDIDATE_ROOT/scripts/verify-approved-release.sh"
```

This verifies candidate code/tests/systemd/config and applies candidate DB migrations only to a disposable SQLite copy. Current production remains online.

Any failure stops the release.

## 7. Remove the bootstrap candidate worktree

After both gates succeed:

```bash
/usr/bin/git worktree remove --force "$CANDIDATE_ROOT"
rm -rf "$TMP_RELEASE_ROOT"
unset CANDIDATE_ROOT TMP_RELEASE_ROOT
```

Do not delete `PREVIOUS_HEAD` or `ZION_DEPLOY_COMMIT`.

## 8. Cutover window

Only now enter the controlled downtime window:

```bash
cd /home/zetta/zion-community-bot

test "$(/usr/bin/git rev-parse HEAD)" = "$PREVIOUS_HEAD"
test "$(/usr/bin/git rev-parse origin/zion-v1)" = "$ZION_DEPLOY_COMMIT"

DASHBOARD_LOAD_STATE="$(
  systemctl show zion-dashboard.service -p LoadState --value 2>/dev/null || true
)"
if [[ -n "$DASHBOARD_LOAD_STATE" && "$DASHBOARD_LOAD_STATE" != "not-found" ]]; then
  sudo systemctl stop zion-dashboard.service
  test "$(systemctl is-active zion-dashboard.service || true)" != "active"
fi

sudo systemctl stop zion.service
test "$(systemctl is-active zion.service || true)" != "active"

GIT_NO_REPLACE_OBJECTS=1 \
/usr/bin/git -c core.hooksPath=/dev/null \
  merge --ff-only "$ZION_DEPLOY_COMMIT"
test "$(GIT_NO_REPLACE_OBJECTS=1 /usr/bin/git rev-parse HEAD)" = "$ZION_DEPLOY_COMMIT"
```

If the fast-forward fails, the old code is still the intended rollback target. Do not use rebase, force-push or an improvised remote rewrite.

## 9. Apply the reviewed release

```bash
ZION_EXPECTED_COMMIT="$ZION_DEPLOY_COMMIT" \
ZION_PREVIOUS_COMMIT="$PREVIOUS_HEAD" \
ZION_GITHUB_GATES_PROVEN=YES \
  bash scripts/apply-zion-v1.sh
```

The apply script revalidates candidate identity, staged runtime, config and DB backup before migration/start.

After the service is stopped, it atomically switches:

```text
/home/zetta/.local/share/zion-community-bot/runtimes/current
```

to the runtime for `$ZION_DEPLOY_COMMIT`.

It also relocates mutable production state to:

```text
/home/zetta/.local/state/zion-community-bot/
```

so the new systemd service no longer needs write access to the code repository or runtime tree.

New verified deployment backups are stored outside the bot-writable state at:

```text
/home/zetta/.local/share/zion-community-bot/deploy-backups/
```

## 11. Failure / rollback

If acceptance fails, stop and use the verified backup directory. It records:

- mandatory `rollback-head.txt`;
- `runtime-before.txt`;
- `runtime-candidate.txt`;
- verified SQLite backup evidence;
- the previously installed systemd unit when present.

Restore the prior local code/runtime/unit/database state deliberately before starting the old service. Never point `runtime/current` at an unrecorded runtime.

Do not force-push `zion-v1` backward. Rollback is local containment; the permanent repair is a forward-fix PR.

See `docs/DEPLOYMENT-MODEL.md` for the full rollback model.
