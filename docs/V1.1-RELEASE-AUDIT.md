# ZION v1.1 — Production Release Gate Audit

Status: **repository release-gate hardening reconciled through the read-only Acer audit; production untouched; external gates pending**.

Release candidate:
- development branch: `zion-v1.1-dev`
- audited base SHA at start: `6c18f4e476f1d3ae16e860c4ae6a64e7327ad830`

Production:
- branch: `zion-v1`
- production SHA at start: `f8c704f16d05c5fba3b55957721b025c9abbaa23`
- production PR: #2, Draft, unmerged.

The v1.1 delta is intentionally treated as a release project, not merely as a green CI run. At audit start it covered 479 commits and 84 changed files relative to production.

## Release invariants

- production remains untouched until an explicit production decision;
- `zion-v1` branch/ruleset protection is mandatory before merge/deploy;
- first-upgrade gates must be runnable while the old production worktree remains unchanged;
- candidate code must bind itself to the exact approved 40-character SHA;
- current production must be healthy before a normal release starts;
- production runtime state and candidate repository content must not be confused during detached-worktree validation;
- dashboard and bot must never claim health from different SQLite files;
- rollback evidence must be outside directories writable by the bot service;
- production `.env` is regular, single-link, mode 0600 and owned by `zetta`;
- no production secret is copied into Git or release evidence;
- production DB migration is preceded by verified SQLite backup/integrity rehearsal;
- the exact `zion-v1.1-dev` candidate is rehearsed before PR #2 may merge, and the actual resulting `zion-v1` SHA is verified again before downtime.

## Findings

### HIGH — installed dashboard could survive cutover on stale runtime/database

The main deploy updated only `zion.service`. If `zion-dashboard.service` was already installed, it could remain on the previous unit/runtime and continue reading the legacy DB while the bot moved to the new state DB.

**Remediation:** an installed dashboard must be stopped in the same cutover. Its prior unit is included in rollback evidence; the candidate dashboard unit is installed with the main unit and the dashboard is restarted only after the main bot is healthy. Both use the same `runtime/current` and state DB.

### HIGH — bot service could write its own repository and secret file

The existing systemd sandbox granted `ReadWritePaths=/home/zetta/zion-community-bot` because SQLite/log state lived in the repository. That also made source code, release scripts and `.env` writable by the bot process. A runtime compromise could therefore persist by modifying code/config that would be consumed on restart.

**Remediation:** the reviewed v1.1 unit forces DB/state/log/lock into `/home/zetta/.local/state/zion-community-bot`, marks the repository read-only and grants write access only to the state directory. The dashboard uses the same state DB.

### HIGH — production Python runtime shared the bot-writable repository boundary

The service executed `.venv/bin/python` from the same repository tree that had to be writable for runtime state. The release procedure also had no clean way to prepare a new exact dependency set without mutating the environment used by the running bot.

**Remediation:** `scripts/prepare-release-runtime.sh` builds/verifies one runtime per approved SHA under `/home/zetta/.local/share/zion-community-bot/runtimes/<sha>`. The service executes `runtimes/current/bin/python`, the runtime tree is read-only to the service, and `current` switches atomically only after the old service stops. Rollback metadata records the prior runtime target.

### HIGH — allowlisted environment keys were not enforced as a closed boundary

The systemd service loads the production `.env` into the process environment. File ownership/mode checks alone do not prevent an unexpected key such as `PYTHONPATH`, `PYTHONHOME` or another process-control variable from changing runtime behavior.

**Remediation:** `.env.example` is the versioned production key allowlist. `scripts/check-env-boundary.py` validates the production file as a private regular single-link UTF-8 assignment file, rejects duplicate/unknown keys and never emits values. Deployment preflight, predeploy and apply all invoke this boundary. Detached candidate worktrees also reject an ignored local `.env`.

### HIGH — non-versioned Git hooks/replace state could alter an approved SHA release

A correct commit SHA is not sufficient if local Git state can change checkout/history behavior or execute code. Active hooks, `core.hooksPath`, replace refs, grafts or dangerous `GIT_*` environment variables can undermine the release boundary.

**Remediation:** `scripts/check-git-release-boundary.py` rejects those local states and shallow release repositories. First-upgrade worktree creation and production fast-forward explicitly use `GIT_NO_REPLACE_OBJECTS=1` and `core.hooksPath=/dev/null`, so hooks/replace refs are neutralized even before the post-check validator runs.

### HIGH — tracked-only Git cleanliness missed untracked import shadowing

The release gates used `git diff --quiet`, which ignores untracked files. Python imports from the worktree, so an unexpected non-ignored file such as a top-level dependency/module shadow could alter candidate or production behavior while the gate still reported a clean tracked diff.

**Remediation:** candidate predeploy, deployment preflight and production apply now require `git status --porcelain --untracked-files=all` to be empty. Runtime artifacts that are deliberately ignored by `.gitignore` remain excluded, while unexpected source-like files block the release.

### HIGH — deploy backups were inside the bot-writable repository

`apply-zion-v1.sh` stored rollback backups under the repository. The systemd sandbox deliberately grants the bot write access to the repository today because DB/log runtime files still live there. A compromised bot process could therefore alter rollback evidence stored in that same writable boundary.

**Remediation:** new deployment backups live under:

```text
/home/zetta/.local/share/zion-community-bot/deploy-backups
```

That path is outside the service's configured `ReadWritePaths`. The apply script requires the directory to be non-symlinked, private and owned by `zetta`.

### MEDIUM — release runtime was range-based instead of reproducible

The repository declared compatible dependency ranges and CI installed the newest matching packages at run time. A later CI rerun or Acer environment could therefore satisfy the same ranges while using a different package set from the one actually audited.

**Remediation:** `requirements.lock` records the full Python package set used by the audited CI environment. GitHub Actions installs that lock, and `check-runtime.py` requires the Acer runtime to match every locked package exactly before any production stop. `pip check` remains an additional dependency-consistency gate.

### MEDIUM — future releases could infer a stale legacy DB from `.env`

After v1.1, systemd forces the live DB/state paths into the isolated state directory. If the historical `.env` still omitted or contained an older DB path, a later predeploy could inspect the wrong database.

**Remediation:** predeploy/apply derive the current production state layout from the root-owned installed `zion.service`. First-upgrade uses the legacy configured/default DB; subsequent state-layout releases use the actual state DB.

### MEDIUM — dependency installation inherited more resolver/index behavior than required

Exact package versions were locked, but ordinary pip invocation still allowed implicit dependency resolution and ambient pip index/config behavior.

**Remediation:** CI and runtime preparation use the complete explicit lock with `--no-deps`, binary wheels only, isolated pip configuration and the explicit HTTPS PyPI index. Published release runtimes have write bits removed and are separately mounted read-only to services.

### MEDIUM — cutover inputs could change after their first validation

The release validated `.env`, HEAD/worktree and runtime early, but did not re-check each immediately before installing units/start.

**Remediation:** apply rechecks exact HEAD, full worktree cleanliness, the saved `.env` SHA-256 plus environment boundary, and `runtime/current` immediately before unit installation/start. State/DB paths also reject symlink redirection.

### MEDIUM — first v1 → v1.1 runbook depended on scripts absent from v1

`deployment-preflight.sh`, `verify-approved-release.sh` and the strict remote-access gate were introduced in v1.1. The old production checkout cannot invoke those files before it has been upgraded.

**Remediation:** the first-upgrade procedure creates a detached temporary worktree at the exact approved v1.1 SHA and runs release gates from that worktree while the production worktree remains on the old commit. `deployment-preflight.sh` now distinguishes its own candidate `SCRIPT_ROOT` from the old production `ROOT` and verifies that its own HEAD equals `ZION_DEPLOY_COMMIT`.

### MEDIUM — predeploy could mix candidate and production-relative defaults

When candidate Python runs from a temporary worktree, `Settings.from_env()` derives default paths from the candidate source root. That can make omitted production path variables point into `/tmp`, while an explicitly configured production knowledge path can cause the predeploy to validate the old knowledge tree instead of the candidate content that will exist after fast-forward.

**Remediation:** predeploy explicitly models production-root defaults for DB/state/log paths. If the effective knowledge path is the normal production repository knowledge directory, validation is redirected to the detached candidate's knowledge directory. Custom external knowledge paths remain validated as configured.

### MEDIUM — normal release could start while production was already down

The deployment preflight previously emitted only a warning when `zion.service` was inactive.

**Remediation:** strict release mode now fails when current production is inactive. `--report-only` remains informational. Existing outage recovery must be handled as an incident, not disguised as an ordinary release.

### MEDIUM — dashboard can point at a different DB than the bot

The dashboard intentionally does not load the secret-bearing bot `.env`; its unit contains an explicit read-only DB path. The bot itself permits a different configured `ZION_DB_PATH`.

**Remediation:** predeploy compares an installed dashboard's effective `ZION_DASHBOARD_DB_PATH` with the production bot DB path and fails on divergence. `apply-dashboard.sh` refuses installation when the bot DB or Wi-Fi interface differs from the reviewed unit values.

### MEDIUM — production environment file boundary did not reject hard links everywhere

Symlink/mode/owner checks existed across the flow, but a hard-linked `.env` was not consistently rejected.

**Remediation:** the centralized environment-boundary validator now requires a regular non-symlink, single-link, mode-0600 file owned by `zetta`; all release gates reuse that same contract.

## 2026-09-20 adversarial re-audit additions

### HIGH — ignored importable artifacts and local Git ignore state could still bypass release cleanliness

**Status: remediated in development.**

The prior cleanliness gate covered tracked and non-ignored untracked files, but Python can execute sourceless bytecode such as a root-level `telegram.pyc` and Git can hide that file through the repository's ordinary bytecode ignore rules. Local `.git/info/exclude` or configured ignore/attribute sources could also hide arbitrary release-relevant files.

`scripts/check-git-release-boundary.py` now fails closed on active local exclude/attribute rules, configured `core.excludesFile`, `core.attributesFile`, `core.fsmonitor`, `core.sshCommand`, `core.worktree`, additional executable Git environment overrides, and ignored importable code outside explicitly non-code runtime/editor roots. Adversarial regression tests prove that an ignored `telegram.pyc` is rejected even when ordinary `git status --untracked-files=all` is empty.

### HIGH — SSH rollback evidence crossed the bot-writable trust boundary

**Status: remediated in development.**

The SSH hardening installer previously copied a root-owned sshd drop-in into the ZION state directory as a `zetta`-owned backup, then trusted that backup for a later root restore on failure. Because the bot writes the state directory, a compromised runtime could tamper with rollback evidence before an operator's privileged restore.

SSH rollback evidence now lives under `/var/lib/zion-community-bot/ssh-hardening-backups/`, with a `root:root 0700` directory and `root:root 0600` backup files. The rollback path no longer relies on bot-writable evidence, and the runbook/tests enforce this boundary.

### HIGH — standalone dashboard installer bypassed the exact-SHA production gate

**Status: remediated in development.**

`scripts/apply-dashboard.sh` previously validated tests but could install and start a production systemd unit from the current worktree without proving the approved production SHA, branch, GitHub branch head, runtime identity or governance attestation.

The dashboard installer is now a one-time bootstrap that requires the full approved SHA, `ZION_GITHUB_GATES_PROVEN=YES`, exact `zion-v1-prod`, clean Git boundary/worktree, local and live `origin/zion-v1` equality, a matching per-SHA `runtime/current`, and an already-running v1.1 bot service. HEAD/worktree/runtime are revalidated immediately before the first `sudo`. Once the dashboard unit exists, later changes must use the controlled main release flow.

### MEDIUM — validation created repository-local bytecode after cleanliness checks

**Status: remediated in development.**

`scripts/validate.sh` used `compileall` and normal imports/tests, which could create `__pycache__` in the release worktree after the initial cleanliness gate. This conflicted with the stricter ignored-bytecode boundary and left local executable cache material beside approved source.

Validation now sets a private `PYTHONPYCACHEPREFIX` under `/tmp`, routes compilation/import/test bytecode there, and removes the temporary cache on exit. The repository worktree is no longer the bytecode cache boundary during validation.

### HIGH — legacy host mutators bypassed governed release and physical-operation gates

**Status: remediated in development.**

Two inherited scripts remained capable of privileged host mutation outside the v1.1 release model: `scripts/apply-systemd.sh` could install/restart `zion.service` directly from the current worktree, and `scripts/apply-wifi-guardian.sh` could install/activate Wi-Fi host components without the dedicated physical-operation authorization boundary.

Both legacy installers now fail closed with exit code 64. Bot deployment must use the exact-SHA controlled flow in `docs/DEPLOYMENT-MODEL.md` / `scripts/apply-zion-v1.sh`. Wi-Fi Guardian host changes require a separately reviewed physical procedure and explicit authorization.

### HIGH — operator executable lookup could undermine exact-SHA Git evidence

**Status: remediated in development.**

Release and host-gate scripts previously invoked `git` through the operator shell's executable lookup. During the first v1 → v1.1 transition, the old bot runs under the same Unix account without the later v1.1 read-only code sandbox, so same-user environment contamination must not be a release trust root.

Critical shell scripts now pin `PATH=/usr/sbin:/usr/bin:/sbin:/bin`, security-sensitive Git decisions use `/usr/bin/git` explicitly, and Python helpers that inventory or record Git state also invoke the absolute Git binary. Regression tests enforce these executable-path boundaries.

### HIGH — Git credential helpers and askpass could execute local code during remote proof

**Status: remediated in development.**

The release boundary disabled hooks, replacement refs, SSH command overrides and other Git-local execution surfaces, but Git authentication itself still had executable extension points. A local `credential.helper` may be an absolute program or shell snippet, and `core.askPass` may point directly to an executable. An isolated reproduction confirmed that `git credential fill` executes an absolute helper even with `GIT_TERMINAL_PROMPT=0`, which is the same non-interactive mode used by release-time remote checks.

`scripts/check-git-release-boundary.py` now rejects `core.askPass`, shell/path/metacharacter credential helpers and inherited `SSH_ASKPASS*` overrides. Simple named helpers with inert arguments remain permitted so the repository does not invent the Acer's authentication mechanism; release scripts already pin `PATH` to system directories, so an allowed named helper resolves only through the reviewed system executable boundary. Regression tests prove the execution primitive and the rejection behavior.

### HIGH — SSH client configuration could execute commands or reroute Git remote proof

**Status: remediated in development.**

For SSH-form GitHub origins, invoking ordinary `git fetch` / `git ls-remote` inherits OpenSSH client configuration. OpenSSH supports command-bearing directives such as `ProxyCommand`, `Match exec`, `KnownHostsCommand` and `LocalCommand`; therefore a same-user `~/.ssh/config` could execute local code or alter the transport before the release proved the remote branch identity. The first v1 → v1.1 fetch was especially sensitive because it occurs before the candidate checker exists locally.

All release-time remote Git proofs now supply a fixed `core.sshCommand` using `/usr/bin/ssh -F /dev/null`, non-interactive batch mode, strict host-key checking and explicit proxy/local-command disablement. `ssh.variant` / `GIT_SSH_VARIANT` overrides are rejected. The first-upgrade runbook performs a candidate-independent bootstrap audit of Git environment/configuration before its first fetch, while the normal Git boundary also rejects disabled HTTPS TLS verification and custom Git CA overrides. Regression tests enforce these transport contracts.

### HIGH — first-upgrade bootstrap could execute a local smudge filter before the Git boundary checker

**Status: remediated in development.**

The first v1 → v1.1 bootstrap created the detached candidate worktree before any v1.1 Git-boundary checker existed on disk. Disabling hooks with `core.hooksPath=/dev/null` is not sufficient: an active local `.git/info/attributes` rule plus a configured smudge filter can execute a local command during `git worktree add`. This was reproduced in an isolated scratch repository: the worktree checkout created the attacker marker while ordinary hooks were disabled.

The first-upgrade runbook now reads `scripts/check-git-release-boundary.py` directly from the exact approved commit using raw `git show <sha>:path` blob access under a sanitized Git environment, runs that checker against the production repository, and only then permits `worktree add`. The runbook also pins bootstrap Git commands to `/usr/bin/git`. The current release tree contains no tracked `.gitattributes`, so the reviewed candidate does not introduce a tracked filter assignment before this boundary.

### HIGH — inherited PYTHON* environment could inject code outside the approved SHA

**Status: remediated in development.**

Pinning the executable path is not sufficient if release-time Python inherits operator variables such as `PYTHONPATH` or `PYTHONHOME`. In an isolated reproduction, a synthetic `sqlite3.py` supplied through `PYTHONPATH` executed before the release probe's intended standard-library import, demonstrating that exact-SHA code and a locked virtualenv can still be bypassed by the caller environment.

`scripts/check-python-release-env.py` now runs under system Python isolated mode (`-I`) and fails closed on any inherited `PYTHON*` variable before release runtimes, migrations, validation or dashboard bootstrap are allowed to execute. `deployment-preflight.sh` records contamination as a failure and explicitly skips non-isolated runtime execution rather than continuing through an already-tainted interpreter environment. Small Tailscale/OpenSSH address probes use `/usr/bin/python3 -I` directly. Regression tests prove the injection mechanism and the new rejection boundary.

### MEDIUM — mutable DB/log paths did not reject pre-positioned hardlinks

**Status: remediated in development.**

The runtime lock already required a regular, single-link file, but SQLite database/WAL/SHM paths and the active log did not consistently enforce the same property. A pre-positioned hardlink inside the writable state directory could therefore alias mutable runtime I/O to another inode while still passing a simple path/symlink check.

SQLite now validates existing database and sidecar files with `lstat` and rejects non-regular or multi-link files before normal use. Logging rejects linked targets and opens the active log with `O_NOFOLLOW` where supported, then verifies regular-file type and `st_nlink == 1` through the opened descriptor before writing. Runtime health also marks symlinked/hardlinked sensitive files unsafe. Regression tests cover DB, WAL/SHM, log and health behavior.

### MEDIUM — exact package versions did not pin the release artifacts themselves

**Status: remediated in development.**

The release lock previously fixed package names and versions, but pip could still accept any repository artifact published for the same version. That left the audited-runtime claim weaker than the exact-SHA application boundary: package identity was version-pinned but artifact bytes were not.

`requirements.lock` now pins the universal wheel for every release distribution by SHA-256. GitHub CI and Acer runtime preparation both use pip `--require-hashes`, `--no-deps` and `--only-binary=:all:`, so an artifact with the correct version but a different digest is rejected before installation. `scripts/check-runtime.py` also fails closed on lock entries without an exact SHA-256 hash, and an existing per-SHA candidate runtime is reusable only when its recorded `requirements-lock.sha256` matches the candidate commit's lock file.

### MEDIUM — first-upgrade rehearsal ordering created a merge/rehearsal cycle

**Status: remediated in development after read-only Acer audit.**

The Acer audit exposed a real procedural contradiction: the handoff required real host/DB rehearsal before any production merge, while `verify-approved-release.sh`, `predeploy-v11.sh` and the first-upgrade runbook required the candidate SHA to already equal `origin/zion-v1`. That made the required pre-merge rehearsal impossible without weakening another gate.

Release scripts now accept only a closed `ZION_RELEASE_SOURCE` enum:

- `candidate` → `origin/zion-v1.1-dev`;
- `production` → `origin/zion-v1`.

Arbitrary refs are rejected. The first-upgrade procedure now requires a full rehearsal of the exact development candidate, including disposable-copy SQLite migration, **before** PR #2 may merge. After an explicitly authorized merge, the actual new `zion-v1` SHA is fetched, staged and verified a second time before any service stop. This preserves both pre-merge evidence and exact post-merge release identity.

### HIGH — bot runtime could read operator GitHub/SSH credentials from the shared Unix home

**Status: remediated in development after controlled Acer preparation.**

The Acer preparation correctly separated release fetch from the administrative GitHub session by installing a repository-scoped read-only deploy key, but both the legacy bot and the reviewed v1.1 service run as Unix user `zetta`. The v1.1 sandbox already made code/runtime read-only, yet it did not make `~/.config/gh` or `~/.ssh` inaccessible. A compromised bot could therefore read the operator's GitHub administrative token or the Git fetch private key even though it could not modify those files.

The v1.1 bot and dashboard units now make `/home/zetta/.config/gh`, `/home/zetta/.ssh`, `~/.git-credentials` and `~/.netrc` inaccessible inside their mount namespaces. Regression tests enforce this confidentiality boundary. The operator retains normal access outside the services.

### HIGH — critical release preflight scripts lost executable Git modes

**Status: remediated in development after controlled Acer preparation.**

The real Acer candidate worktree exposed that `scripts/deployment-preflight.sh`, `scripts/predeploy-v11.sh` and `scripts/remote-access-preflight.sh` were tracked as mode `100644`, while the release flow itself requires those scripts to be executable. Content-level CI did not catch the mode mismatch.

All three scripts are now tracked as `100755`. A regression test reads the Git index directly and fails unless every critical release preflight script retains mode `100755`.

### MEDIUM — Mistral credential lifecycle depended on static environment configuration

**Status: remediated in development.**

The previous AI integration loaded `MISTRAL_API_KEY` from the long-lived production `.env` into immutable startup settings. That coupled provider-secret rotation to environment editing and process restart, kept the credential inside the broad bootstrap-secret surface, and offered no dedicated runtime integrity boundary for the provider key.

The candidate now removes the Mistral secret value from `Settings` and rejects a non-empty legacy `MISTRAL_API_KEY`. The production path is fixed in code at `/home/zetta/.local/state/zion-community-bot/secrets/mistral-api-key`; it is not configurable through `.env`. The dedicated `SecretStore` requires a canonical 0700 directory and 0600 regular single-link file owned by the service user, rejects symlink/hardlink/alias conditions, reads with `O_NOFOLLOW` where available, and publishes rotations atomically with rollback on durability/verification failure.

An explicit `ZION_ADMIN_USER_IDS` operator can arm `/setmistralkey` only in the private ZION chat. The next non-command message is captured in memory for at most 120 seconds, deleted from Telegram before provider validation or local persistence, and blocked from the ordinary moderation/AI/SQLite pipeline. Deletion failure is fail-closed. Validation uses the official non-redirecting `GET https://api.mistral.ai/v1/models` credential check. Rotation validates first and publishes second; Action Ledger failure rolls the secret mutation back. `/clearmistralkey CONFIRM` is also audit-atomic.

The secret is never written to SQLite, action metadata, logs, dashboard state or deployment backups. The dashboard systemd unit makes the secrets directory inaccessible. Legacy rollback requires the secret to be cleared and verified missing before older same-user code may start; the key is intentionally not backed up and must be reprovisioned after recovery.

The flow is documented honestly: the operator-selected secret message does transit Telegram private chat before ZION deletes it. The application does not claim that Telegram never handled the credential.
